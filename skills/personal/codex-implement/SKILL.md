# Codex への実装委譲

実装を Codex に任せても最終品質を落とさないための協業プロトコル。品質は次の 3 点で担保する:

1. **設計は Claude がやる** — Codex は「よく仕様化された作業の実行」に徹してもらう。設計判断を丸投げしない。
2. **指示書は単体で完結させる** — Codex はこの会話を見られない。指示書だけ読めば迷わず実装できる粒度で書く。
3. **検収は必須ゲート** — Codex の成果物は「自分が書いたコードのコミット前」と同じ厳しさでレビュー・検証する。検収を通っていない変更は完了扱いにしない。

ユーザーの発言からモードを判別する。「やらせて」「依頼して」「指示書を」→ 依頼モード。「終わった」「検収して」「レビューして」→ 検収モード。

## 依頼モード: 作業指示書を作る

### 1. 先に自分で設計する

指示書を書く前に、関係するコードを読んで実装方針を自分で決める。触るファイル、変更の継ぎ目、データの流れ、既存パターンとの整合。ここを省くと指示書が曖昧になり、Codex の設計判断に品質が依存してしまう — それでは委譲する意味の分だけ品質が下がる。

自分で実装する場合と同じ深さで調査すること。調査中に「これは Codex に任せるには判断が多すぎる」と感じた部分は、指示書で選択肢を潰しておくか、その部分だけ自分で実装して残りを委譲する。

### 2. 指示書を書く

`docs/codex-work-orders/YYYY-MM-DD-<slug>.md` に作成する。テンプレートは [references/work-order-template.md](references/work-order-template.md) を読んで使う。

書くときの要点:

- **受け入れ基準は検証可能な形で書く**。「正しく動くこと」ではなく「X を入力すると Y が表示される」「`scripts/codex-powershell.ps1 verify-index-exp` が OK を返す」のように、Codex 自身が達成を確認でき、検収時に Claude が機械的にチェックできる文にする。
- **スコープ外を明記する**。Codex は気を利かせて周辺もリファクタリングしがち。触ってほしくないファイル・やってほしくない変更を書く。
- **リポジトリ共通ルールは書き写さない**。Codex は `AGENTS.md` を自動で読むので、そこにあるルール（`index.html` の apply_patch 限定、backup/verify スクリプト、BOM 禁止など）は「AGENTS.md に従うこと」の一行で足りる。タスク固有の制約だけ指示書に書く。
- **完了報告の書式を指示する**。テンプレートに含まれる「完了報告」節を Codex に埋めさせる。変更ファイル一覧・設計判断・実行した検証とその結果。これが検収の入口になる。

### 3. ユーザーに手渡す

指示書のパスを伝え、Codex セッションに渡す一文（例: `docs/codex-work-orders/2026-07-08-xxx.md を読んで実装してください`）を提示して、このターンを終える。Codex の完了を待つ間このセッションで何かを並行する必要はない。

## 検収モード: Codex の成果を検収する

ユーザーが「終わった」と言ったら、`docs/codex-work-orders/` で status が「依頼中」の指示書を探して開始する。

1. **完了報告と差分を読む**。指示書の完了報告節 → `git status` / `git diff` の順。報告と実際の差分が食い違っていたら（報告にないファイルが変わっている等）、まずそこを掘る。
2. **受け入れ基準を一つずつ検証する**。指示書に書いた検証コマンドを実際に実行する。Codex が「実行した」と報告していても再実行する — 検収の意味はそこにある。
3. **コード品質をレビューする**。自分がこの diff をコミットしようとしていると思って見る: 既存パターンとの整合、エッジケース、命名、不要な変更の混入。プロジェクトに /code-review 相当のスキルがあれば使ってよい。
4. **判定する**:
   - 軽微な問題（typo、スタイル不一致、小さい抜け）→ その場で自分で直す。差し戻すより速い。
   - 設計レベルの問題や大きい抜け → 指示書に「差し戻し」節を追記し（何が・なぜダメか・どう直すか）、status を「差し戻し」にしてユーザーに再手渡しする。
   - 問題なし → status を「完了」にする。

検収結果は、確認した受け入れ基準・見つけて直した問題・残課題をユーザーに報告する。全基準を検証せずに「問題なさそう」と報告しない。

## 品質の考え方

Sonnet/Opus が直接実装するときの品質は「設計・実装・自己検証が同じ頭の中で閉じている」ことから来ている。委譲するとこのループが切れるので、切れ目を文書（指示書・完了報告）で補い、最後に Claude の検証で閉じ直す。指示書の曖昧さと検収の甘さがそのまま品質低下になる — 手を抜くならこのスキルを使わず自分で実装するほうがよい。
