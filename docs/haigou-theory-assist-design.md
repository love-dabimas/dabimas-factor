## 0. このドキュメントの位置づけ

繁殖牝馬を起点に、代ごとに種牡馬を選び、その組み合わせで成立する配合理論・有効な因子・クロスを
3代先まで確認する機能（ゲームの「配合理論補助」に相当）を、ダビふぁくへ実装するための設計である。

種牡馬・繁殖牝馬の選択にはダビ娘を使う。**判定はすべてダビふぁく側で行い、ダビ娘へは結果だけを
postMessage で渡す。** ダビ娘に判定ロジックは置かない。

### 0.2 要件（ユーザーの指示の要約）

1. ゲームの配合理論補助と同じことを、現代的な画面でやりたい。
2. 入口はホーム画面のダビ娘タイルの隣。
3. 種牡馬の選択はダビ娘を流用する。
4. 繁殖牝馬・種牡馬とも、候補に自家製馬を含める。単体検索画面にも出す。
5. カードに出すのは レア／馬名（因子付き）／脚質・成長・実績・気性・安定・底力・健康・適正力・距離／
   血統表 だけ。それ以外は既存馬からも消す。
6. 血統表は既定で畳み、ボタンで開く。
7. 選択中のカードは暗くし、上に「選択を解除する」を重ねる。
8. 配合理論（完璧・超完璧・奇跡・至高）で候補を絞り込める。0件のときは素直に0件と出す。
9. クロスの詳細は既定で非表示。

## 1. 確認済みの事実（実装前に必ず読む）

本章はすべて実データ・実コードで確認した内容である。推測は §8 に分けてある。

### 1.1 理論判定は系統コードだけで計算でき、ゲームの表示と一致した

ダビふぁくの `vue/logic/theory/compatibility.js` を Node 上でそのまま実行し、ダビ娘の
`horselist.json` の実データを通した。

| 入力 | 値 |
| --- | --- |
| 繁殖牝馬 スターベガ の4枠 | `Ma Hi Ha Sw` |
| 種牡馬 スターアルタイル-瓏覇- の見事4枠 | `Ma Sw Hi Ha` |
| 種牡馬の面白4枠 | `Ns He He Ro` |

判定結果は次のとおりで、ゲーム画面の表示（完璧な配合）と一致した。

- 見事4枠の一致 4件 → 見事な配合が成立
- 面白側8枠のユニーク 7種類（7以上で成立）→ 面白い配合が成立
- 両方成立 → **完璧な配合**

さらにスターベガに対して完璧になる種牡馬を全2,480頭から求めたところ6頭で、
すべてスターアルタイルのバリエーションだった。これはゲームの種牡馬リスト画面
（瓏覇・覇煌・翔燕・天煌に「完璧な配合」）と一致する。

**判定に血統表の展開は不要である。** 面白・見事の系統コードだけで足りる。

### 1.2 繁殖牝馬の理論用4枠は「面白側と同じ4枠」

繁殖牝馬側は面白・見事とも同じ4枠を使う（`vue/logic/plan/plan-diagnosis.js` の
`dam: [damLines, damLines.slice()]` と同じ）。その4枠は次で得られる。

```
繁殖牝馬の4枠 = [Paternal_t, Paternal_jik[0], Paternal_ht, Paternal_jik[1]]
```

`Paternal_mig` ではない。スターベガの場合、この式は `Ma Hi Ha Sw` を返し、
ゲーム画面の「見事な配合系統」の表示と一致する。いっぽう `Paternal_mig` は
`Ma Ec Ph` で、別の値である。以前この点が未確定で保留していたが、本件で確定した。

#### 盤面のセルとの対応（2026-09-14 訂正）

**上の式の並びと、盤面セル `[1,3,5,7]` の並びは同じではない。** 実データ500頭で
突き合わせた結果はこうなる（例外0）。

```
盤面セル [1, 3, 5, 7] = [Paternal_t, Paternal_ht, Paternal_jik[0], Paternal_jik[1]]
                          ↑ セル3が Paternal_ht、セル5が jik の前半
```

つまり真ん中2つが入れ替わっている。**自家製馬からダビ娘の4フィールドを組むときは
`paternalHt = セル3`、`paternalJik = セル5 ＋ セル7` にすること。**

判定そのものへの影響は無い。面白4枠の並びを入れ替えて
`detectMatchedTheories` を 16,000 組に掛けたが、結果が変わった組は0だった
（この4つは順序を見ない条件になっている）。Phase 1 が
`prepareMareLines = linesAt(board, [1,3,5,7])` のままゲームと一致したのはこのためである。

影響が出るのは**ダビ娘へ渡す値**のほうで、`Paternal_ht` を取り違えると
カードの面白の並びと母父系統での検索がずれる。Phase 4a の検収でこれを踏んだ。

### 1.3 見事系統の数は種牡馬4つ・繁殖牝馬3つ

`horselist.json` 全件で例外がなかった。

| 対象 | 頭数 | `Paternal_mig` のコード数 | `Paternal_jik` のコード数 |
| --- | ---: | ---: | ---: |
| 種牡馬 | 2,480 | すべて 4 | すべて 2 |
| 繁殖牝馬 | 499 | すべて 3 | すべて 2 |

したがって見事の表示枠は固定4マスにせず、頭数に応じて伸縮させる。

また、**繁殖牝馬は血統表スロット側に見事のコードを持たない**（該当セルが空）。
ダビ娘の実カードも牝馬のときは見事のコードを描画しない作りになっている。

#### 見事の3つ・4つは盤面のどのセルか（2026-09-14 追記）

自家製馬にはダビ娘のマスターが無いので、見事のコードは盤面から組む必要がある。
`expandHorseBoard` の結果と `Paternal_mig` を全件突き合わせた結果は次のとおり。

| 対象 | 見事のコード | 盤面のセル |
| --- | --- | --- |
| 種牡馬 | 4つ | 9 / 11 / 13 / 15 |
| 繁殖牝馬 | 3つ | **9 / 13 / 15**（11 を使わない） |

繁殖牝馬 499 頭すべてで 9・13・15 が一致し、例外は無かった
（`11,13,15` などの並びで偶然一致する馬も居るが、全頭で成立するのは 9・13・15 だけ）。
**自家製繁殖牝馬の見事も 9・13・15 で組む。** なお見事は表示だけに使い、
理論判定には使わない（判定に使うのは §1.2 の4枠）。

### 1.4 速度（実測）

計測環境は開発機の Node。判定コードはダビふぁくの実物を使用した。

計測環境は開発機の Node。判定コードはダビふぁくの実物を使用した。
**データの形で20倍違う**ので、どちらの数値かに注意する。

ダビ娘のデータ（`Paternal_*` が最上位にある平たい形）での値。

| 処理 | 実測 |
| --- | --- |
| 種牡馬2,480頭の事前準備 | 3.5 ms（マスター読込時に1回） |
| 母側データの準備 | 0.76 ms |
| 全2,480頭の理論判定（面白〜超完璧） | 25.4 ms |
| 繁殖牝馬499 × 種牡馬2,480 ＝ 1,237,520組 | 8.6 秒 |

**ダビふぁくのデータ**（親系統が `descendants` の中にあり、`expandHorseBoard` で
16セルの盤面を組む必要がある）での値。**Phase 1 が実際に動くのはこちら。**

| 処理 | 実測 | いつ走るか |
| --- | --- | --- |
| 盤面の組み立て＋親系統8枠の抽出（全2,433頭） | 554 ms | **1回だけ** |
| **理論判定だけ（全2,433頭）** | **22〜32 ms** | 母が変わるたび |
| `judgeInbreed`（クロス判定）1回 | 0.5〜0.67 ms | — |
| 同上を全候補に流す | **1.3〜1.7 秒** | 母が変わるたび |

いずれも詳細チャンクが全件メモリ上にある前提（起動後の `prefetchHorseDetails()` 完了後）。

**種牡馬の盤面は母に依存しないので、1回組んで使い回す。** 盤面から取り出した
面白4枠・見事4枠だけを持っておけばよく、その大きさは全2,433頭で240KB程度である。
これをやらないと母が変わるたびに554msかかるが、やれば25ms級に落ちる。
配合理論補助は世代ごとに母が変わるため、ここは必ず効かせる。

**面白〜超完璧は、母が決まった時点で全候補を判定してしまってよい。** 25ms なら
「見えている行だけ計算する」等の遅延評価は要らない。
重いのはクロス判定（1.5秒）で、そちらだけ扱いを分ける。

### 1.5 完璧が成立する繁殖牝馬は少ない

全繁殖牝馬について、完璧になる種牡馬の数を数えた。

| 指標 | 値 |
| --- | --- |
| 平均 | 1.1 頭 |
| 最多 | 40 頭（メゾンフォルティー） |
| **完璧が0頭の繁殖牝馬** | **387 / 499 頭（78%）** |
| 参考: 見事の平均 / 最多 | 3.9 頭 / 47 頭 |
| 参考: 超完璧の合計 | 72 件（最多13頭） |

つまり完璧で絞ると、多くの場合0件になる。0件は0件として素直に出す（要件8）。
次点への自動切り替えや代替提案は行わない。

### 1.6 自家製馬には能力値が存在しない

ダビ娘のカードは実在馬の実測データ（`card.stats` の脚質・成長・実績ほか、`card.abilityData` の非凡）
を前提に組まれている。いっぽうダビふぁくの自家製馬（`vue/app/methods/horse-loading.js` の
`createSavedHorseSummary`）が持つのは `name / sex / parentLine / son / factors` だけである。

これは実装の不足ではない。走らせていない仮想の産駒には、その値自体が存在しない。
したがって自家製馬の能力9項目は「ー」で埋める。レア枠は空欄にせず「自家製」ラベルに差し替える。

なお**実在馬でも繁殖牝馬は脚質〜距離が元データの時点で空欄**である（自家製馬の空欄とは別の話）。

### 1.7 仮想産駒（2代目以降の母）の4枠は、4つのフィールドから導ける

世代を繋ぐには「1代目の産駒の理論用4枠」が要る。血統盤面を組む必要はなく、
親2頭のフィールドを読むだけでよい。

```
産駒の4枠 = [種牡馬の Paternal_t,   種牡馬の Paternal_ht,
             繁殖牝馬の Paternal_t, 繁殖牝馬の Paternal_ht]
```

産駒の血統で位置を辿るとこうなる。親系統は父系で受け継がれるので、
産駒の父（＝種牡馬そのもの）の親系統は種牡馬の `Paternal_t` に等しい。

| 産駒から見た位置 | 実体 | 取り出し元 |
| --- | --- | --- |
| 父 | 種牡馬そのもの | 種牡馬の `Paternal_t` |
| 父母父 | 種牡馬の母父 | 種牡馬の `Paternal_ht` |
| 母父 | 繁殖牝馬の父 | 繁殖牝馬の `Paternal_t` |
| 母母父 | 繁殖牝馬の母父 | 繁殖牝馬の `Paternal_ht` |

**ゲーム画面と一致することを確認済み。** スターベガ × スターアルタイル-瓏覇- の
1代目産駒について、この式は `Ns He Ma Ha` を返す。ゲーム画面の2代目
「1代目配合の繁殖牝馬」に表示される面白い配合系統・見事な配合系統は
Nasrullah / Matchem / Herod / Hampton で、集合として一致する。

3代目まで同じ式で繋がることも確認した（2代目で完璧になるのは2頭、
そのうちサーハリールイスを選ぶと3代目は0頭）。

**この結果、理論判定に関する限り世代の連結は O(1) である。** `composeVirtualMareBoard`
による盤面の組み立ては要らない。ただし**クロス・危険・至高・奇跡には盤面が要る**ので、
そちらは従来どおり組む。

### 1.8 その他

- `judgeInbreed`（`vue/logic/inbreed/inbreed-detector.js`）は純関数で、
  `nodeTable` が無いときは名前一致に縮退する。ダビ娘のデータは馬名を持つので届く。
- 奇跡の判定は `compatibility.js` の `if (perfect)` の内側にある。
  **完璧が成立していない馬は奇跡になりえない。**
- 至高は `judgeInbreed` の `sameNameSpecialChecks` から来る。安い条件での前ふるいができない。
- 危険な配合は他のすべての理論を上書きして表示される（`PRIORITY` が 999）。

## 2. 設計方針（先に結論）

1. **判定はダビふぁく側に一本化する。** ダビ娘へは「馬のキー → 理論ID」の対応表だけを
   postMessage で渡す。ダビ娘は絞り込みと表示だけを行う。
2. **判定は2段構えにする。** 安い判定（面白〜超完璧）で全候補をふるいにかけ、
   高い判定（危険・至高・奇跡）は残った候補だけに流す。
3. **至高と危険だけは例外で、全候補にクロス判定が要る。** 母が確定した時点で
   バックグラウンドで流し始める。
4. **カードの項目は要件5のとおりに絞る。** 既存馬からも非凡・天性・因子カウント表・
   配合理論マークを外す。
5. **自家製馬は postMessage で注入する。** ダビ娘のマスターには存在しないので、
   親から渡して候補へ混ぜる。
6. **入口はホーム画面の「馬を探す」区画**。既存のダビ娘タイルの隣にタイルを1枚足す。

## 3. 判定の置き場所と受け渡し

### 3.1 なぜダビふぁく側で判定するか

| 観点 | ダビふぁくで判定（採用） | ダビ娘で判定 |
| --- | --- | --- |
| ロジックの重複 | 1箇所。既存の実装をそのまま使う | 理論判定・クロス判定・盤面組み立てを TypeScript へ移植。必ずズレる |
| 自家製馬 | ダビふぁくが持っているデータをそのまま使える | 親から全血統を送る必要がある |
| 盤面のセル対応 | 既存の `setDataForPedigree` / `composeVirtualMareBoard` を使うので考えなくてよい | ダビ娘の15スロットとダビふぁくの32セルの対応を新たに決める必要がある（§8.1） |
| 転送量 | 理論IDの対応表だけ。2,480件で約10KB | 判定に要る全データ |

移植コストの問題ではなく、**判定を2箇所に置くと必ず食い違う**ことが理由である。

### 3.2 2段構えの判定

| 段 | 対象理論 | 前ふるい | 実測コスト |
| --- | --- | --- | --- |
| 1段目（安い） | 面白 / よくできた / 見事 / 完璧 / 超完璧 | 不要（全候補に流す） | 25ms / 2,480頭 |
| 2段目（高い） | 奇跡 | 1段目で完璧の候補だけ（最多40頭） | 約28ms |
| 2段目（高い） | 至高 / 危険 | **効かない。全候補が対象** | 1.3〜1.7秒 |

危険は全理論を上書きするため（§1.8）、バッジを正確に出すなら結局全候補にクロス判定が要る。
「先に安い理論を出して、あとから危険へ差し替える」方式は誤認を招くので採らない。

至高・危険の1.5秒は母が確定した時点で走らせ、終わるまでは該当チップを操作不可にする。
実機（iPhone）ではさらに時間がかかるため、Worker か時間分割の要否は実測して決める（§8.2）。

### 3.3 メッセージ仕様（`docs/dabimusume-integration-design.md` §4 への追加分）

既存のメッセージはそのままで、次を足す。すべて `v: 1` を付け、
`event.origin === location.origin` のときだけ処理する規則は既存と同じ。

| 向き | type | 中身 | いつ |
| --- | --- | --- | --- |
| 親 → ダビ娘 | `dabimas:custom-horses` | `{ v, horses: [...] }` | `hello` への返事と、自家製馬が変わったとき |
| ダビ娘 → 親 | `dabimas:candidates` | `{ v, rows: [...] }` | 検索データを読み終えた直後に1回 |
| 親 → ダビ娘 | `dabimas:theory-map` | `{ v, mareKey, chips, entries }` | 母が確定して判定が終わるたび |

#### なぜ候補の系統をダビ娘から送り返すのか（2026-09-14 に決めた）

理論判定に要るのは候補1頭につき系統コード8つだけである（面白4・見事4）。これは
**ダビ娘の `horselist.json` が平らなフィールドとして既に持っている**
（`Paternal_t` / `Paternal_ht` / `Paternal_jik` / `Paternal_mig`）。

一方ダビふぁく側で同じものを得ようとすると、親系統が `descendants` の中にあるため
候補ごとに16セルの盤面を組む必要があり、**詳細チャンク23本（2.7MB）の読み込みと
554ms の展開**が要る（§1.4）。理論マップのためだけにこれを払うのは重い。

そこで**ダビ娘が持っている値をそのまま親へ渡す。** 2,979行 × 8コードで 90KB 程度、
`postMessage` の構造化複製なら数msで済む。理論の規則（`compatibility.js`）は
ダビふぁく側の1か所に置いたままにできる。

```js
{
  type: "dabimas:candidates", v: 1,
  rows: [["1774722353-0", "Ns", "He", "HeRo", "MaSwHiHa"], ...],
  //      horseKey,       t,    ht,   jik,    mig
}
```

- ダビ娘が送るのは**マスターの馬だけ**。自家製馬の系統はもともと親が持っている。
- 送るのは検索データを読み終えた直後の1回だけでよい（一覧は変わらないため）。
- 親はこれを受け取るまで理論チップを出せないので、`theory-map` はこの後に送る。

#### `dabimas:theory-map` の中身（2026-09-14 に確定）

```js
{
  type: "dabimas:theory-map", v: 1,
  mareKey: "1774722353-1",        // どの繁殖牝馬に対する表か
  chips: [                        // 出すチップと、その並び。理論の知識は親が持つ
    { key: "PERFECT",       label: "完璧",   bit: 1, pending: false },
    { key: "SUPER_PERFECT", label: "超完璧", bit: 2, pending: false },
    { key: "MIRACLE",       label: "奇跡",   bit: 4, pending: false },
    { key: "SUPREME",       label: "至高",   bit: 8, pending: true  },
  ],
  entries: [["1774722353-0", 5], ["ch_a1b2-0", 1]],  // [horseKey, ビットの論理和]
}
```

- `mareKey`: 古い母の結果を採用しないための照合に使う。ダビ娘は自分が今開いている
  母と違うキーの表を捨てる。
- `chips`: **理論の定義はすべて親（ダビふぁく）が持つ。** ダビ娘は key の意味を知らず、
  ラベルを出してビットで絞り込むだけにする。理論を増減しても、直すのは親だけで済む。
- `entries`: 1頭につき1行。値は**成立した理論のビットの論理和**である。
  1つの理論だけを持たせるのでは足りない — 奇跡は完璧が前提（§1.1）なので、
  1頭が複数のチップに該当しうる。論理和なら「完璧で絞る」と奇跡の馬も残る。
- **該当0のチップしか無い馬は `entries` に載せない。** ダビ娘は載っていないキーを
  「どの理論も成立しない」として扱う。§1.5 のとおり該当する馬はごく少ないので、
  2,979頭ぶん送るより桁違いに小さくなる（完璧6頭の母なら数行で済む）。
- `pending: true` のチップは、ダビ娘が操作不可にして「計算中」と分かる見た目にする。
  **計算していない状態を0件と表示してはいけない。** 計算が終わったら
  `pending: false` にした表を送り直す。

**件数はダビ娘が数える。** 親は該当キーだけを渡し、チップに出す頭数はダビ娘が
「いまの検索結果 ∩ そのビットを持つ馬」で求める。レアや系統で別に絞り込んでいる
ときに、チップの数字と一覧の数が食い違わないようにするため。

#### `dabimas:custom-horses` の中身（2026-09-14 に確定）

ダビ娘は `HorseRecord` を組み立てて自分の一覧に混ぜる。親は判定と表示に要る分だけ送る。

```js
{
  type: "dabimas:custom-horses", v: 1,
  horses: [{
    key: "ch_a1b2-0",         // ダビ娘での horseKey。HorseId は "ch_a1b2"
    gender: "0",              // ダビ娘の Gender（"0" 種牡馬 / "1" 繁殖牝馬）
    name: "スターアルタイル瓏覇",
    category: "ボールドルーラー系",   // 子系統。無ければ空文字
    categoryHt: "",
    paternalT: "Ns", paternalHt: "He",
    paternalJik: "HeRo",       // 面白4枠は [T, jik前半, Ht, jik後半]（§1.2）
    paternalMig: "MaSwHiHa",   // 種牡馬はセル 9/11/13/15、繁殖牝馬は 9/13/15（§1.3）
    factors: ["", "", ""],     // 本人の因子コード
    pedigree: [[名前, 子系統, 系統コード, 因子コード配列], ...15行],
  }],
}
```

- **`HorseId` は `ch_` で始める。** マスターの `HorseId` は数字だけなので、これで
  絶対に衝突しない。ダビふぁく側の `musumeLink.fromMusume` も `ch_` を通すようにする。
- 能力9項目・非凡・天性・レアは存在しない（§1.6）。ダビ娘は「ー」で描く。
- 自家製馬は端末ごとに違い、件数も少ない。`hello` のたびに送り直す。

## 4. 画面仕様

モックで確認済み。実物は `docs/haigou-theory-assist/` のHTMLを参照（付録A）。

### 4.1 種牡馬カードの項目

出すのは次だけ。既存馬・自家製馬とも同じカードを使う。

| 項目 | 実在馬 | 自家製馬 |
| --- | --- | --- |
| レア | そのまま | 「自家製」ラベルに差し替え |
| 馬名（因子付き） | そのまま | そのまま |
| 脚質・成長・実績・気性・安定・底力・健康・適正力・距離 | そのまま | すべて「ー」 |
| 血統表（15行） | そのまま | そのまま |

**消すもの**（既存馬からも消す）: 非凡、天性、全因子カウント表、1薄め2薄め表、配合理論マーク。

### 4.2 面白・見事の表示

カード右上に2行で出す。オレンジが面白、青が見事。見事は牡4つ・牝3つで伸縮する（§1.3）。

カードは760px基準で作られ、画面幅に合わせて縮小される（375pxの端末で0.42倍）。
そのため**カード内の基準サイズを20pxに取る**。0.42倍で約8.5pxとなり、馬名と同じ大きさになる。
ここを11pxで作ると実質4.6pxで読めない。26pxでは馬名より目立ちすぎる。

繁殖牝馬は血統表側に見事のコードを持たないため、表示は `Paternal_*` から組み立てる（§1.2、§1.3）。

### 4.3 血統表

既定で畳み、「▼ 血統表を見る」で開く。自家製馬も同じ。開閉時にカードの実高さを測り直す。

### 4.4 選択と選択解除

- カードをタップすると選択。同時に選べるのは1頭で、別のカードをタップすると選択が移る。
- 選択中はカードを暗くし、中央に「選択を解除する」を重ねる。この状態は選択中ずっと維持する。
- **解除ボタンは縮小の外に置く。** カード内に入れると0.42倍で押せなくなる。
  モックでの実寸は153×52pxで、指で押せる大きさを確保できている。

### 4.5 配合理論での絞り込み

- チップは 完璧 / 超完璧 / 奇跡 / 至高 の4つ。各チップに該当頭数を出す。
- 判定は「いまの繁殖牝馬と組んだときに成立する理論」である。
  ダビ娘が既に持っている `card.theory`（その馬単体の素質フラグ）とは**別物**なので混同しない。
- **0件のときは素直に0件と出す。** 「該当なし／◯◯な配合になる種牡馬はいませんでした。」
  次点の提案や自動切り替えはしない（§1.5、要件8）。
- 至高・危険の計算が終わるまでは、該当チップを操作不可にして計算中と分かるようにする。
  計算していない状態を0件と表示してはいけない。

### 4.6 配合理論補助の画面（ダビふぁく側の新規画面）

3世代を縦に並べる。各世代は次の3状態を取る。

| 状態 | 表示 |
| --- | --- |
| 選択済み | 繁殖牝馬 ＋ 種牡馬 ＋ 判定結果 |
| 未選択 | 繁殖牝馬 ＋「＋ 種牡馬を選ぶ」（押すとダビ娘のピッカーが開く） |
| 待ち | 「前の代の種牡馬を選ぶと使えるようになります」。操作不可 |

判定結果のブロックは次の3つ。

1. **成立した配合理論** — 代表1件をバッジで出す。`matchedTheories` と `displayedTheory` は
   分けて保持する（既存の `compatibility.js` が既にそうなっている）。
2. **因子** — ダビふぁくの既存の集計ヘッダー
   （`vue/components/header/factor-summary-header.js`）と同じ表にする。
   並びは 短 速 底 長 走 中 強 雷 堅 難 適 丈 早 晩、色は `css/style.css` の `.f01`〜`.f14`、
   行はニトロ（`#00abab`）とクロス（`#aa0000`）、2桁ゼロ詰め。
3. **クロスの詳細** — **既定で非表示**。「▼ クロスの詳細を見る（N件）」で開く。
   件数はボタンに出すので、開かなくても件数は分かる。危険な重なりには「危険」タグを付ける。

1代目で選んだ種牡馬と繁殖牝馬から生まれる産駒が、そのまま2代目の繁殖牝馬になる。
前の代を変えたら、その代より後ろの仮想血統と結果をすべて破棄して組み直す。

### 至高・危険を Phase 5 に送る理由

完璧・超完璧・奇跡は系統コードだけで決まり、全候補でも 22〜32ms で終わる（§1.4）。
一方、至高と危険は `judgeInbreed` が要り、全候補で 1.3〜1.7 秒かかる。Phase 4 で
一緒に入れると、この待ち時間の設計（チャンク分割か Worker か）が混ざって検収しづらい。

当初 **Phase 4 は至高チップを `pending: true` で出す**方針だったが、実機で
「ずっと計算中のまま」と指摘された。計算していないものを計算中と見せるのは
誤りなので、**計算を入れる Phase 5 パート2 までチップ自体を出さない**（3つにする）。
危険も同じ理由で Phase 5 へ送る。

Phase 5 パート2 では、軽い判定（系統コードだけ・25ms）をこれまでどおり即座に送り、
重い判定（`judgeInbreed`・全候補で 1.3〜1.7 秒）は分割して裏で進めてから
2通目の `dabimas:theory-map` で上書きする。至高チップはその2通目で
`pending: false` になる。詳細チャンク（2.7MB）は起動時の `prefetchHorseDetails` が
裏で読み終えているので、ここで新しく取りに行く必要はない。

**Phase 4 の時点での既知の穴**: 危険な配合になる組み合わせも、完璧・超完璧・奇跡の
チップに数えられてしまう（危険は `judgeInbreed` が要るので Phase 4 では判定していない）。
Phase 5 で危険を計算に入れて、チップから除くところまで面倒を見る。

## 9. 本番へ出さずに統合版を試す

`main` へ push した時点で本番に出てしまうため、確認は公開前にローカルで行う。
iframe は同一オリジンでないと動かないので、ダビ娘のビルドをこのリポジトリの下へ置いて
1つのサーバーから配信する。本番と同じ URL 構造（`/dabimas-data/dist/`）を再現する形になる。

### 9.1 手順

1. **ダビ娘をビルドする**（`dabimas-data` リポジトリ、統合用の枝で）。
   本番の週次ワークフローと同じベースパスを渡す。

   ```
   VITE_BASE_PATH=/dabimas-data/dist/ npm run build
   ```

   ベースパスを省くと絶対パスが `/` 基準になり、埋め込み先で読み込めない。

2. **ビルド結果をこのリポジトリへ置く。** `dabimas-data/dist/` に丸ごとコピーする。

3. **ダビふぁく側を、統合対象の枝にしておく**（ダビ娘統合＋本機能が入った状態）。

4. **配信する。** `start-lan.bat` を実行する。リポジトリのルートを `0.0.0.0:8080` で配信し、
   `Cache-Control: no-store` が付くので古い JS が残らない。

5. **実機で開く。** 同じ Wi-Fi の iPhone から `http://<PC の IP>:8080/index.html`。
   IP は `start-lan.bat` が画面に出す。

### 9.2 この方法で確認できないもの

| 項目 | 理由 |
| --- | --- |
| Service Worker | LAN の http は secure context ではないため登録されない |
| オフライン動作 | 同上 |
| iPhone のホーム画面アプリとしての挙動 | 同上（manifest と SW に依存する） |

Service Worker まで含めて確認したい場合の選択肢は次のとおり。

| 方法 | 使える範囲 | 注意 |
| --- | --- | --- |
| PC で `http://127.0.0.1:8080/` を開く | SW もオフラインも確認できる | 実機では確認できない |
| https のトンネル（cloudflared 等） | 実機で SW まで確認できる | 起動中は URL が外部から到達できる。本番ではないが公開状態になる |
| 別リポジトリへ staging として公開 | 実機で SW まで確認できる | 本番 URL ではないが公開になる |

`docs/dabimusume-integration-design.md` §12 の未確認項目（iPhone のホーム画面アプリで
機内モードでも開けるか）は、この制約により公開後にしか確認できない。

### 9.3 注意: `dabimas-data/` の除外がこの端末にしかない

`dabimas-data/` を Git の対象外にしている設定は `.git/info/exclude` に入っており、
**`.gitignore` には無い**。`.git/info/exclude` は共有されないため、別の端末や
クローンし直した環境では未追跡ファイルとして見えてしまう。

その状態で気づかずコミットすると、7.4MB のダビ娘のビルドがダビふぁく側へ入り、
`main` へ merge した時点で本番に出る。**除外は `.gitignore` へ移すこと**（1行）。

## 10. 受け入れ基準

1. ホームの「馬を探す」区画に、ダビ娘の隣から配合理論補助へ入れる。
2. 繁殖牝馬を選ぶと、種牡馬未選択の1代目が表示され、2・3代目は操作できない。
3. 種牡馬を選ぶと、成立した配合理論・因子表・クロスの詳細（畳んだ状態）が出る。
4. 1代目の産駒が2代目の繁殖牝馬として入り、2代目が操作できるようになる。
5. 1代目の種牡馬を変えると、2代目以降の結果が破棄される。
6. カードに出るのは §4.1 の項目だけで、非凡・天性・因子カウント表・理論マークが無い。
7. 自家製馬が実在馬と同じカードで候補に並び、能力9項目が「ー」、レア枠が「自家製」になる。
8. 血統表が既定で畳まれ、ボタンで開閉できる。自家製馬も同じ。
9. カードをタップすると暗転して「選択を解除する」が出る。押すと選択が外れる。
10. 配合理論チップで絞り込める。スターベガなら完璧7頭・超完璧0頭になる。
11. 0件のときに「該当なし」と出る。次点への自動切り替えが起きない。
12. 至高・危険の計算中は該当チップが操作不可で、0件とは区別できる。
13. 母を変えると、前の母の判定結果が混ざらない。
14. 375px 幅で横スクロールが出ず、面白・見事が読める大きさで出る。
