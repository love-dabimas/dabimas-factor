## 背景

フェーズ2d・2eで「盤面に父母が揃う位置には、その2頭の子を組み立てる」という規則を入れた。
ただし適用範囲は**牝馬15枠とルートセルだけ**で、男系15枠は対象外にした
（`vue/logic/pedigree/board-refs.js` の「男系祖先には適用しない」のコメント）。

2eの検収で、**同じ穴が男系に残っている**ことが分かった。以下の2件はどちらも実データで再現済みである。

### ケースA: 中間セルへ積み上げると、自動生成される馬が判定に参加しない

操作:

1. 父側**④**へ **パーソロン1971** を置く
2. 父側**⑥**へ **スイートルナ** を置く
3. 母側**②**へ **シンボリルドルフ** 本人を置く

このとき父側③には `★１薄めパーソロン1971` が自動生成される。
これは「父がパーソロン1971・母がスイートルナ」の individual であり、
**シンボリルドルフの全兄妹**にあたる。

| | 着色 | シンボリルドルフのクロス |
|---|---|---|
| 現行 | `[4,18,10,28]` | **なし** |
| 期待 | `[2,17,10,28]` | 血量 **37500**、出現 `["FF","F"]` |

`★N薄め` は父側の偶数セル（②③④⑤⑥⑨⑪⑫⑬⑮…）へ置いたときに自動生成される。
`while (isEven(reverseNum))` で cellNo から上へ遡って作られるためで、
奇数セル（③⑩⑭⑯＝母父の位置）だけを使う積み上げでは発生しない。
ユーザー報告4件目の手順が母側の奇数セルだけを使っていたので、今まで表に出ていなかった。

### ケースB: 自家製種牡馬の父が、盤面へ置き直すと unknown に戻る

操作:

1. 父側**②**へ **パーソロン1971**、父側**⑩**へ **スイートルナ** を置いて
   **自家製種牡馬**として保存する（保存馬の父＝父側①の `★１薄め`＝シンボリルドルフの全兄妹）
2. 別の盤面の父側**④**へその自家製種牡馬を置く（その父は父側⑮に来る）
3. 母側**②**へ **シンボリルドルフ** 本人を置く

| | 着色 | シンボリルドルフのクロス |
|---|---|---|
| 現行 | `[16]` | **なし** |
| 期待 | `[14,17,16]` | 血量 **28125**、出現 `["MMFF","F"]` |

保存レコードの `fatherRef` は2eで `{kind:"implied", ...}` になった。
しかし `descendants[0].identityRef` は `{kind:"unknown"}` のままなので、
盤面へ置き直すと父側⑮のセルが unknown になり判定に参加しない。
**保存レコードは正しい情報を持っているのに、盤面へ展開する経路で落ちている。**

### 影響の測定

完全な試作（下記パート1〜3すべて）を当てて、実データ2300盤面で現行と比較した。

| 盤面の種類 | 件数 | 差分 |
|---|---|---|
| 通常（種牡馬×繁殖牝馬をルートに選ぶ） | 800 | **0件** |
| 母側積み上げ | 500 | **0件** |
| 父側積み上げ | 500 | **0件** |
| 中間セル積み上げ（`★N薄め` が出る） | 500 | **0件** |

無関係な馬同士が全兄妹になることはまず無いので、
**実際に全兄妹関係があるときだけ結果が変わる**。ケースA・Bのように構成した盤面でのみ差が出る。

## 実装方針

3パートすべてを入れて初めてケースBが直る。ケースAはパート1〜2だけで直る。

### パート1: `resolveBoardRefs` を男系にも適用する

`vue/logic/pedigree/board-refs.js`

```javascript
    // 深い母から補完し、最後にルートへ適用する。男系祖先には適用しない。
    for (let slot = MARE_PATHS.length - 1; slot >= 0; slot -= 1) fillImplied(MARE_PATHS[slot]);
    fillImplied("");
```

を、31位置すべてを**パスの長い順**に処理する形へ置き換える。

```javascript
    // 位置 p の父は p+"F"、母は p+"M"。どちらも p より深いので、
    // パスの長い順に処理すれば依存関係が解決済みになる。
    const ALL_PATHS = ["", ...SIRE_PATHS, ...MARE_PATHS].sort((a, b) => b.length - a.length);
    ALL_PATHS.forEach(fillImplied);
```

`fillImplied` の中身は変えない（既に `unknown` のときだけ埋める形になっている）。
長さ4（5代目）の男系は父が6代目にあたり盤面に無いので、結果として埋まらない。これは正しい。

### パート2: 判定側が男系の解決結果を読むようにする

`vue/logic/inbreed/inbreed-detector.js` の `buildSideOccurrences`。

男系15枠は今 `ref: cellRef(horse)` とセルから直接引いている。
これだとパート1で解決した implied が使われない。

```javascript
              occurrences.push({
                ...horse,
                ref: boardRefsFor(sideOffset).refByPath.get(path) ?? cellRef(horse),
```

`refByPath` は男系パスに対して既定で `cellRef(horse)` を入れているので、
プレースホルダ以外のセルでは値が変わらない。

### パート3: 保存レコードの `descendants` の unknown を埋める

`vue/logic/horses/saved-horse-builder.js`

`descendants[i]` は保存元盤面のセル `DESCENDANT_CELL_IDS[i]` の内容である。
各セルの「その側から見たパス」は次のとおり。

| descendants の添字 | セル | 側 | パス |
|---|---|---|---|
| 0〜7 | 0, 1, 2, 4, 5, 3, 6, 7 | 父側 | `""`, `"F"`, `"FF"`, `"FFF"`, `"FMF"`, `"MF"`, `"MFF"`, `"MMF"` |
| 8〜14 | 17, 18, 20, 21, 19, 22, 23 | 母側 | `"F"`, `"FF"`, `"FFF"`, `"FMF"`, `"MF"`, `"MFF"`, `"MMF"` |

（母側ルートのセル16は `descendants` に入らない。`motherRef` が担当する）

`context.nodeTable` があるときだけ、**`identityRef` が `unknown` の要素に限って**
`sireBoard` / `damBoard` の `refByPath` から引いた値で置き換える。
使えている値には触らない（2eと同じ方針）。

## 受け入れ基準

`json/` 配下の実データで確認すること。数値はすべて Claude 側で実測済みである。

### 1. ケースAが直る【必須】

背景のケースAの盤面で:

- `inbreedColorIndexes === [2, 17, 10, 28]`
- `crosses` に **シンボリルドルフ / 血量 37500 / 出現 `["FF", "F"]`**
- `dangerous === false`

### 2. ケースBが直る【必須】

背景のケースBの盤面で:

- `inbreedColorIndexes === [14, 17, 16]`
- `crosses` に **シンボリルドルフ / 血量 28125 / 出現 `["MMFF", "F"]`**

パート3を入れないとここは直らない。パート1〜2だけでは
父側⑮のセルが `{kind:"unknown"}` のまま残る（実測済み）。

### 3. 既存の判定が動かない【必須・不変条件】

実データで、少なくとも次の4種類・各500盤面以上を現行（918e55e）と比較し、**差分0件**であること。

- 通常盤面（種牡馬×繁殖牝馬をルートに選ぶ）
- 母側積み上げ（ルートが「ワタシノヒンバ」）
- 父側積み上げ（ルートが `★N薄め`）
- 中間セル積み上げ（父側④などへ置いて `★N薄め` が2つ以上できる）

比較対象は `count` / `dangerous` / `inbreedColorIndexes` / `selfAncestorWarningIndexes` /
`factorCd` / 群数 / 全クロスの代表ノード・血量・出現（index・path・世代・mareSlot・side・refのkind）。

### 4. 通常盤面の保存レコードが動かない【必須・不変条件】

通常盤面から保存したレコードの
`fatherRef` / `motherRef` / `mareRefs` / `mares` / `descendants` が**1件も変わらない**こと。

### 5. フェーズ2eの受け入れ基準がそのまま通る【必須】

`scripts/verify-p2e-refactor.cjs` と `scripts/verify-p2e-saved.cjs` が通ること。
とくに、ユーザー報告4件目の盤面が
`colored=[1,12,30,14,26]` / シンボリルドルフ 血量28125 `["F","MMMM"]` のままであること。

### 6. resolver が無いときに壊れない【必須】

`buildSavedHorseRecord` を第5引数なしで呼んでも、`window.Dabimas.pedigreeNodes` が null でも動くこと。

## 検証時の注意

- **新旧で同じ盤面を評価しているか確かめること。** Claude 側で一度、
  乱数の呼び出しを盤面生成のクロージャの中に置いてしまい、
  新旧で別の盤面を比べて「500件中108件の差分」という誤った数字を出した。
  盤面の材料は先に確定させてから両方に渡すこと
- **クロスは父側と母側の間でしか成立しない。** 同じ側に全兄妹を2頭置いても出ない。
  Claude 側でこれも一度間違えた
- **ローカルサーバの取り違え**: ポート8766・8767 に古いリポジトリのコピーを配る
  `python -m http.server` が残っていることがある
- **ServiceWorker のキャッシュ**: `CACHE_NAME` を bump しないと古いJSが配られ続ける
- **改行コード**: このリポジトリは LF
