## 1. 結論

全兄妹は、提示された3例の期待値を満たすように「本人は別個体、直近の父と母がそれぞれ完全一致」で判定する。父母の比較に全兄妹判定を再帰適用しない。自家製馬にも個体識別と父母参照を持たせ、積み上げても保持する。クロス成立と画面表示を分離し、牝馬の出現は内部判定へ残して表示だけ抑制する。

「自家製の積み上げは1代まで」という上限を実装してはならない。制限されるのは全兄妹関係を親の同一性へ昇格させることであり、血統の保存・探索・伝播自体は再帰的に行う。

## 3. 指定3例の調査結果・期待値

### ケース1：ダンスインザダークとダンスパートナー

父母は実マスタ上で一致する。両馬を左右に含む血統では全兄妹クロス対象とする。通常版同士の最小入力は現行でも内部成立する。一方、祖先セルへの繁殖牝馬選択には次の不具合がある（レビュー§3、コードの該当条件も照合済み）。

1. setDataForPedigreeが付ける括弧付きsubNameをisBroodmarePlaceholderHorseが検出し、buildSideOccurrencesから祖先群を除外する。通常クロスまで欠落する。
2. その位置に表示されるのは牝馬の父であり、選択した牝馬本人の出現がない。
3. 祖先を変更してもルートのmareNodeIdsが更新されず、変更前の血統が残る。

この3点を先行フェーズで修正する。除外の解除だけ、保存処理だけの修正では不十分。

期待：ダンスインザダーク側の該当牡馬セルにクロス表示。ダンスパートナー本人と、その代わりに表示される祖先セルには、この全兄妹成立を理由とする表示を付けない。

### ケース2：スイートルナ×パーソロン→自家製牝馬A、A×トウカイテイオー

ルドルフの父母はパーソロンとスイートルナ。Aの父母が同じゲーム血統の同一性へ解決されれば、Aとルドルフは全兄妹として成立する。A本人にルドルフのIDを付与する必要はない。

| パーソロンの選択 | 指定期待値 |
|---|---|
| 1971等の年号版 | ルドルフとの全兄妹クロス成立 |
| 覇煌等の因名版 | この組み合わせでのルドルフ全兄妹クロス不成立 |

年号版を合格とするのは、ユーザーが提示したゲーム上の期待値に基づく本修正の受入要件である。父の比較に必要な血統同一性への解決を行う。すべての年号付き商品を確認済みとはしない。

現行ではAが本人ID欠落・☆除外・マスタ限定親照合に阻まれる。期待：トウカイテイオー側のルドルフを表示し、A側は全兄妹クロス表示なし。通常の別祖先クロスは独立に判定する。

### ケース3：エアグルーヴ×サンデー→A、A×キンカメ→B、B×ドゥラメンテ

Aはアドマイヤグルーヴと父母が一致し得るが、アドマイヤグルーヴ本人ではない。Bとドゥラメンテの母比較は「自家製A」と「マスタのアドマイヤグルーヴ」で不一致。よってドゥラメンテ本人との全兄妹クロスは不成立。

期待：ドゥラメンテをこの関係でクロス表示しない。Bも表示しない。キングカメハメハ等の別祖先で生じるクロスまで一括で消さない。現行の自家製除外でも偶然不成立となるため、不成立だけでは正しい実装の証明にならない。

対照ケース：マスタのアドマイヤグルーヴ×対応するキンカメの娘Cは、ドゥラメンテと直近父母が一致するため全兄妹候補になる。ケース3と合わせて判定し、再帰的な置換がないことを確認する。

## 4. データ修正仕様

### 4.1 個体と表示を分離する

既存nodeIdはマスタvariantの参照として維持し、独立した判定用refを追加する。自家製のnodeIdへ既存実馬IDを代入しない。

```javascript
// 新設する概念スキーマ。既存フィールドは維持する。
{
  pedigreeSchemaVersion: 2,
  identityRef: { kind: 'custom', id: 'ch_<永続UUID>' },
  fatherRef: { kind: 'master', nodeId: '<選択したvariant>' },
  motherRef: { kind: 'master', nodeId: '<選択した牝馬>' },
  sex: '1'
}
```

- 参照種別はmaster、custom、edit、unknown。editは保存参照として区別するが、クロス上は公式因名版相当とし、ベース馬のpedigreeIdを継ぐ。独立した実馬とは扱わない。
- ★薄め馬など個体を特定できない表示ノードはunknown。unknown同士、null同士を一致させない。☆保存馬は名前の印ではなく保存レコードからcustomとして解決する。
- customの既存ch_idを再利用し、読み込み・表示ごとにUUIDを再発行しない。
- 保存された同一個体を再利用すると同じref。別個体として新規保存すれば別ref。
- 表示用selectedHorseやセルindexを個体識別子にしない。
- 自家製親はcustom refを保持し、共有・エクスポートに必要な祖先レコードも同梱する。外部参照だけに依存して削除後に壊れる形式を避ける。
- descendants、牝馬枠へidentityRefを伝播する。旧mares配列と併存するmareRefs配列を追加し、同じ15枠の順序を使う。表示行数は増やさない。

### 4.2 年号／因名の親比較キー

親比較専用のキーを定義する。表示用variant nodeId、因子参照、通常クロスの本人ID、奇跡グループを一括正規化してはならない。

| 親参照 | 親比較キーの扱い |
|---|---|
| マスタの通常版／検証済み年号版 | 同じ実馬の通常血統を表すキーへ解決 |
| マスタの因名版 | 因名variantを区別したキー。通常血統キーへ落とさない |
| 自家製 | customの永続ID。父母が似ていてもマスタへ置換しない |
| 未解決 | unknown。比較成立に使わない |

通常血統キーは概念上 `master-base:<pedigreeId>` とし、-00の実在を必須としない。因名版は `master-variant:<nodeId>` とする。キーの一致は親比較用途に限定する。

配布済みnodeFields.subnameを使用する。null／空文字、または数字だけの文字列（/^[0-9]+$/）を通常・年号版とし、それ以外の登録済みsubnameは因名版とする。ノード自体が未解決ならunknown。Pythonの変更・JSON再生成・追加メタデータは不要。

マスタの父母はparentsOfが返すpedigree IDからmaster-baseキーを得る。自家製の父母は保存refからキーを得る。サンデー1989・1995はともに通常血統キーへ解決し、-00が存在しても年号版の一致を妨げない。

本人がダンスインザダーク燕闘の場合、その父母はダンスパートナーの父母と一致する。一方、自家製の父がパーソロン覇煌ならルドルフの父とはキーが違う。「比較対象本人の版」と「比較する親の版」の違いであり、例外ではない。

エディット馬の親比較キーはedit:<保存ID>を用い、通常血統キーと一致させない。公式因名版相当という意味は通常版への正規化をしないこと。公式版との完全なvariant同定情報がない限り名前だけで同じキーを付けない。

現行の選択肢に因名版しかない馬は、その因名版を父にして通常血統の父を持つマスタ馬の全兄妹を作れない。将来の選択肢まで固定する説明ではない。

## 5. 判定処理

1. 保存・読み込み時にrefを復元し、マスタと自家製の統合resolverを構築する。
2. 左右ルートを含む既存探索範囲へ出現を展開する。牝馬、自家製も対象。★／☆という名前を理由に除外しない。
3. 保存個体・variantの参照同一性と、クロス上の同一馬判定と、直近父母一致判定を別関数にする。マスタ／editのクロス上の同一馬は既知のpedigreeId一致、custom同士は永続ID一致で判定する。customをマスタへ同一化しない。
4. 親キーを取得できる双方の父同士・母同士を完全一致で比較する。isFullSiblingを親に対して呼ばない。
5. 既存の祖先重複除外・クロス群構成へ接続する。branchParentNodeIdだけでなくbranchParentRefを扱い、自家製の欠落を防ぐ。
6. 内部結果を確定した後、表示対象を抽出する。

```javascript
function isFullSibling(a, b, resolver) {
  if (!a || !b || resolver.sameCrossHorse(a.ref, b.ref)) return false;
  const ap = resolver.parents(a.ref);
  const bp = resolver.parents(b.ref);
  if (!ap || !bp) return false;
  return resolver.sameKnownParent(ap.father, bp.father)
      && resolver.sameKnownParent(ap.mother, bp.mother);
}
```

sameKnownParentは未知値をfalseとし、親比較キーの一致だけを見る。全兄妹関係の推移閉包を個体同一性へ使わない。

### 5.1 名前フォールバックと同一馬分類

nodeTableがある経路では名前一致へのフォールバックを禁止する。全兄妹から同一pedigreeIdを除外する変更と、同一馬判定へpedigreeId一致を追加する変更は同時に行う。片方だけ変更して既存variantクロスを消してはならない。isSameBranchも同じ同一馬／全兄妹の関係を使用するが、親比較キーには流用しない。

同名の別customは同一馬ではない。ただし直近父母が一致すれば全兄妹として成立し得る。偽陽性テストは父母が異なる個体を使う。brosDataはnodeTable経路で使わず、既存のマスタ未読込時の縮退用途に限って残す。新設custom／unknownを名前照合へ落とさない。

### 5.2 resolverの受け渡し（確定）

`judgeInbreed(selected, inbreedExceptions, nodeTable, resolver)` とする。resolverは読み取り専用で、nodeTableとcustom・editレコードを包む。セルにはidentityRefと性別を伝播し、父母の解決はresolverで行う。グローバル保存状態を判定関数内から読み取らない。

画面側inbreed-ui.jsと工程診断側plan-diagnosis.jsの両呼び出しを変更する。工程で合成する自家製牝馬は一意な一時refと父母を診断用registryへ登録する。board[0]をnullにして牝馬情報を失わないよう、ルートref／牝馬枠を独立して渡す。診断用refは同じ診断内で安定させ、保存済みcustom IDと衝突させない。

### 5.3 セル差し替え時の再構築

選択イベントで、選択した馬本人のref・性別・配置pathを表示セルと別に保持する。括弧付きsubNameから馬名検索して本人を復元しない。全選択操作、削除、復元、左右差し替えで当該側の非表示牝馬枠を再計算し、古いサブツリーを置換する。

各側ルートをpath空文字、世代を1+path.lengthとする。例えば母側cell19（MF）へダンスパートナーを選ぶ場合、本人はその父セルの親位置Mに置き、表示上のサンデーはMFのままとする。選択した牝馬が占めるpathは操作時に明示し、表示の父と同一pathにしない。画面由来の系譜と選択元マスタが矛盾する部分は明示選択を優先する。

非表示牝馬は同じside・pathごとに1出現へ統合する。同じ馬でも異なるpathは別出現として保持する。5代目自身の親比較用参照は保持するが、6代目をクロス出現へ増やさない。

## 6. 牝馬側のクロス表示を出さない仕様

「牝馬側」は全兄妹ペアの牝馬本人の出現を指す。血統表の下半分全体を消す意味ではない。下半分にいる牡馬祖先の正当なクロス表示は維持する。

| 対象 | 内部crosses | 全兄妹由来の文字色・ハート・強調 |
|---|---|---|
| 牡馬本人／牡馬祖先 | 含める | 既存方式で表示 |
| 牝馬本人／牝馬祖先 | 含める | 表示しない |
| 牝馬を代替表示する父・母父等のセル | 本来の祖先として別判定 | 牝馬全兄妹の代理強調はしない |

- occurrenceにsex（male/female/unknown）、ref、side、path、generation、displayIndexを保持する。index=nullを牝馬判定の代用にしない。ルート牝馬は表示indexを持つため。
- 関係種別exact／fullSiblingを保持する。全兄妹成立によるfemale出現を表示用配列へ入れない。
- 同一セルが別の有効なクロスで表示対象になる場合、その表示は消さない。表示対象は関係ごとに求めて最後に和集合を取る。
- 牝馬名が括弧付きsubNameに含まれる祖先へ代理表示しない。
- UI都合でcrosses.occurrencesから牝馬を削除しない。血量・dangerous・至高は完全な内部結果を入力にする。表示分類は残った表示セル数ではなく、非表示出現も含む関係から決定する。片側1セルでも全兄妹はsiblingGroupsへ出す。
- 既存count／legacyHiddenCrossCountの契約を維持し、新しいhasCrossは追加しない。非表示クロスが存在してもcountが0にならないことを検収する。
- 因子集計buildInbreedFactorCountsと表示対象配列を渡す呼び出しは変更しない。牝馬は現行では因子を持たないため、牝馬の非表示化による因子数差はない。全兄妹で表示される牡馬の因子は従来どおり数える。将来、自家製牝馬に因子付与を許す場合はこの前提を再検討する。
- 牝馬の因子を新規に捏造しない。自家製を既存牡馬へ置換して因子を複製しない。

## 7. 理論と既存機能への影響

面白・見事・よくできた・完璧・超完璧等の判定式と表示優先順位を本変更で書き換えない。クロスの同一性・親キーの変更を奇跡／至高の本人照合へ無条件に流用しない。

理論がクロス結果を参照する場合、検出漏れの修正に伴う入力差は生じ得る。表示抑制だけで理論・因子・血量が変化しないことを保証する。「理論は従来どおり」は判定規則の維持を意味し、既存不具合で欠落した入力を固定する意味にはしない。

至高の現行式は維持する。全兄妹（自家製を含む）が群へ混ざれば同一実馬条件を満たさず不成立。以前は☆除外で誤成立していた結果が解消されることを受け入れる。危険の式と優先順位も維持し、自家製の同一個体・全兄妹を含むことで危険になる変化を受け入れる。工程診断も同じ結果を使う。

selfAncestorWarningの対象・判定は変更しない。今回のref対応を理由にcustomや非表示牝馬への警告対象を拡張しない。奇跡など他の理論のセル位置照合・親系統照合も変更しない。

| pedigree-cells.js等の選択・復元経路 | セル変更時に牝馬枠と配置情報を再構築 |
| inbreed-counts.js／Python生成処理／配布JSON | 変更なし |

レビューの確定条件「統合版は未公開」に従い、旧保存の自動マイグレーションは実装しない。旧データを削除・推測補完する意味ではない。参照不足のデータはunknownとして扱い、新仕様で保存したデータを検収対象とする。

共有は32セルのid収集だけでは足りない。identityRefから参照されるcustom・editを収集し、その父母を再帰的に辿って必要レコードを同梱する。訪問済み集合で重複と循環を防ぐ。受取側はregistry登録後に盤面を復元する。参照先が欠落した場合はunknownとし、別の同名馬へ接続しない。

フェーズ1の回帰差分は、欠落していた出現の復元と古い牝馬枠の除去で説明できることを条件とする。古い血統による誤クロスが消える場合まで「既存クロス消失ゼロ」を要求しない。変更した牝馬経路と無関係な差分は不合格とする。

## 10. 代替案と注意点

- 採用：マスタ参照と自家製参照を統合するresolver。保存・表示・判定を分離できる。
- 不採用：全兄妹相手のマスタIDへ置換。ケース3を誤成立させる。
- 不採用：積み上げ回数で一律制限。正しい深い祖先クロスも消してしまう。
- 不採用：牝馬を内部候補から削除。ケース1・2と因子等の計算が欠落する。
- 本仕様はJavaScriptで実装する。現行リポジトリのAGENTS.mdを遵守する。
- 未知のvariantを含む全馬完全再現は本調査で確定していない。指定例の合格と、ゲーム全体の同等性は別に評価する。
