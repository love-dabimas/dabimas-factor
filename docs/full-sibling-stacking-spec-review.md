## 0. 結論

設計の骨格 — 個体refと表示の分離／親比較に全兄妹判定を再帰させない／牝馬は内部に残して
表示だけ抑制 — は妥当で、指定3例の期待値もこの設計から導ける。

ただしこのまま Codex に渡すと次の3種類の事故が起きる。

1. **不要な工程をやらせる。** §8 が要求する「Python生成処理への variant 分類メタデータ追加」は不要。
   配布済みの `subname` だけで通常/年号版と因名版を判別できる（本書 §2）。
   なお §4.2 の親比較キーの方針自体は正しい（ゲーム内観測で確定済み）。
2. **ケース1が直らない。** 仕様書はケース1の失敗原因を特定できていない。真の原因は
   `isBroodmarePlaceholderHorse` による祖先サブツリーの丸ごと除外で、仕様書はこれを
   表示上の注意としてしか扱っていない（本書 §3）。
3. **偽陽性クロスを作り込む。** §5-2「★／☆を理由に除外しない」を素直に実装すると、
   `isExactSameNode` の名前フォールバックが開いて別個体が同一馬として結合する（本書 §4）。

加えて、影響範囲の表（§8）から工程診断・selfAncestorWarning・mareNodeIds の
更新経路が抜けている（本書 §5）。

**2026-09-08 追記**: 未決だった判断はすべて確定した（§8・§9）。実装は2フェーズに分け、
既存バグ（§3）を先行フェーズとして単独で検収する。

## 2. §4.2 の親比較キーは方針として正しい。ただし Python 生成処理の変更は不要

### 2.1 実測

`json/dabimasFactor-details/` 全23チャンクを走査した結果:

- 祖先枠（descendants）**43,710件すべて** が、その pedigreeId の「`-00` があればそれ、
  無ければ variant_code 最小」というノードを使っている。非該当 0 件。
- 牝馬枠（mares）の非 null **42,841件すべて** も同じ。非該当 0 件。
- nodeId は例外なく `pedigreeId + "-" + variant_code` の形（10,278件で逸脱 0件）。
  suffix と subname の対応も完全に一致する。`00`→subname なし（8,629）、
  `01/02/03`→年号（319）、`10` 以上→因名（1,330）。混在は1件も無い。

これは偶然ではなく仕様である。`scripts/pedigree_master_source.py:296`
`representative_node_id()` が「`variant_code == "00"` を優先、無ければ最小」を返し、
`sire_slots` / `mare_slots` がそれを使っている。

### 2.2 帰結

- **マスタの祖先枠に因名版が現れることはない。** 仕様書 §4.2 末尾の「マスタ自身の父母参照が
  pedigree ID しかないので親の variant 情報が失われている可能性がある」は、実データ上は起きない。
- 通常版／年号版と因名版の区別は、**すでに配布済みの `nodeFields.subname` だけで判定できる**。
  追加メタデータは要らない。

```javascript
// pedigree-node-table.js に足すだけ。
// subname が null か数字だけ（= 通常版 or 年号版）→ 通常血統キー
// subname が名前（= 因名版）                      → variant キー
function parentComparisonKey(nodeId) {
  const node = nodeTable.getNode(nodeId);
  if (!node) return null;
  const sub = node.subname;
  const isBase = !sub || /^[0-9]+$/.test(String(sub));
  return isBase ? "master-base:" + node.pedigreeId : "master-variant:" + nodeId;
}
// マスタ側の親: parentsOf(nodeId).father（pedigree ID）→ "master-base:" + それ
// 自家製側の親: 保存した fatherRef の nodeId → parentComparisonKey()
```

- 検証: この判定は nodeId の suffix 規則（`0x` = 通常/年号、`1x` 以上 = 因名）と
  **10,278ノード全件で完全に一致**する（不一致 0 件）。どちらで実装しても同じだが、
  将来 suffix が `21` 等へ伸びても壊れない subname 判定を推奨する。
- パーソロンのように `-00` が実在しない馬でも `master-base:0000333257` という
  概念キーで一致する。仕様書 §4.2 の「`-00` の実在を必須としない」はそのまま正しい。
  受入テスト B05 は自然に通る。
- **§8 の「Python生成処理 | variant 分類／親比較用メタデータの出力」行は削除してよい。**
  10Kノードの JSON 再生成と再検証という重い工程が1つ丸ごと消える。

### 2.3 年号版の扱いはゲーム内観測で確定した（2026-09-08）

観測結果:

- **サンデーサイレンス1989 × エアグルーヴ の仔 は アドマイヤグルーヴ と全兄妹になる**
- **サンデーサイレンス1995 × エアグルーヴ の仔 も アドマイヤグルーヴ と全兄妹になる**

（アドマイヤグルーヴ = サンデーサイレンス × エアグルーヴ。マスタ上の父の祖先枠は
`0000333862-00` で、1989 = `-01`、1995 = `-02`。ゲームの選択候補に通常版サンデーサイレンスは
存在せず、1989 / 1995 と因名版のみ。）

**結論: 仕様書 §4.2 の案（年号版は通常血統キーへ解決）が正しい。**
本レビュー初版で提案した「canonical node 方式」は誤りなので採用しないこと。
`-00` が実在する馬でも、年号版は通常版と同じ親比較キーになる。

既知の観測をこの規則で並べると全部説明がつく。

| 自家製の父 | ノード | 親比較キー | 相手の父の枠 | 結果 |
|---|---|---|---|---|
| パーソロン1971 | `0000333257-01` | `master-base:0000333257` | ルドルフの父 `0000333257` | 成立（観測一致） |
| パーソロン覇煌 | `0000333257-10` | `master-variant:0000333257-10` | 同上 | 不成立（観測一致） |
| サンデーサイレンス1989 | `0000333862-01` | `master-base:0000333862` | アドマイヤグルーヴの父 `0000333862` | 成立（観測一致） |
| サンデーサイレンス1995 | `0000333862-02` | `master-base:0000333862` | 同上 | 成立（観測一致） |

**副次的に分かること**: 「因名版しか買えない種牡馬」は、マスタ馬の全兄妹を作る父としては
永久に使えない。選択できる種牡馬 1,143 pedigree のうち **187 pedigree** が該当する
（アイリッシュリヴァー、アンダースタンディング等）。覇煌の観測と整合するので
仕様どおりと考えてよいが、仕様書に「意図した挙動」として1行残しておくこと。

### 2.4 非対称性の説明が足りない

受入テスト A03「ダンスインザダーク燕闘版を使用 → 全兄妹成立」と
B03「父を覇煌に変更 → 不成立」は、どちらも因名版なのに結論が逆で、理由が書かれていない。

実際には整合している（**本人**が因名版なら pedigreeId が同じで親も同じ → 成立、
**親**が因名版なら親比較キーが違う → 不成立）が、この非対称は明文化しないと
Codex がどちらかに寄せて壊す。§4.2 に一段落追加すべき。

## 3. ケース1の真の原因が特定できていない【最重要】

仕様書 §3 ケース1 は「非表示牝馬の伝播・プレースホルダー変換・表示出口を合わせて検証する」
としか書いておらず、どこが落ちているかを特定していない。実行して特定した。

### 3.1 繁殖牝馬を祖先セルに置くと、そのサブツリー全体がクロス判定から消える

`horse-cell.js:226` により、各側の localIndex **3 / 5 / 7 / 9 / 11 / 13 / 15** のセルは
種牡馬＋繁殖牝馬のリスト（`horses[0]`）を出す。つまり祖先セルに繁殖牝馬を置ける。

置くと `setDataForPedigree` が `id !== 0` 側の分岐（pedigree-builder.js:451〜）に入り、
そのサブツリー **15セル全部** に `subName: "(その牝馬名)"` を付ける。
牝馬本人のセルは存在せず、その位置には **牝馬の父** が入る。

そして `isBroodmarePlaceholderHorse`（inbreed-detector.js:95）が、
`buildSideOccurrences` でこれら全部を出現から除外する。

**実行確認**（父側ルート=ダンスインザダーク、母側ルート=エアグルーヴ、
母側 cell19 に ダンスパートナー を選択）:

```
現行:                       inbreedColorIndexes = []   crosses = 1
プレースホルダー除外を外す:  inbreedColorIndexes = [1,19,5,29,3,23,7,31]  crosses = 5
  サンデーサイレンス     cell1 (F)   × cell19 (MF)
  アンダースタンディング  cell5 (FMF) × cell29 (MFMF)
  ニジンスキー           cell3 (MF)  × cell23 (MMF)
  キートゥザミント       cell7 (MMF) × cell31 (MMMF)
```

つまり全兄妹以前に、**牝馬を祖先に置いた瞬間、そのサブツリー由来の通常クロス
（サンデーサイレンス 2×3 等）が4本まるごと消えている**。
画面上「クロスが1つも出ない」という見た目になるのはこれが原因。

仕様書はこのセルを §3 で「その代わりに表示される祖先セル」、§6 で
「牝馬名が括弧付き subName に含まれる祖先へ代理表示しない」と、
**表示側の注意としてしか扱っていない**。実際には検出側の全損である。

**いつ壊れたか（特定済み）**: `git log -S` で追うと、この除外を
`buildSideOccurrences` へ適用したのは **b869028「同一家系枝の重複クロスを除外」
（2026-09-02）** である。それ以前の実装では、

- `(牝馬名)` セルは **同名クロスの検出ループには参加していた**
  （名前一致ループに `isBroodmarePlaceholderHorse` のチェックが無い。現在も無い）
- 除外していたのは全兄妹ループだけで、その分は冒頭の `broodmareGroups` ブロック
  （`type: 'broodmare-stallion-sibling'`）が専門に担当していた

b869028 が nodeTable 経路を新設したとき、**除外だけを引き継いで専用ブロックを
引き継がなかった**。`broodmareGroups` が作る `recognizedCrosses` は、
nodeTable 経路の表示出口（`crosses` と exception だけを見る）から参照されない。
これが 3.1 の正体である。フェーズ1の作業指示にはこの経緯を書くこと。

**検証手法の前例**: b869028 の完了報告
`docs/codex-work-orders/2026-09-02-inbreed-branch-exclusion.md` は、
固定 seed `0x20260902` で実データ4000組を生成し `crosses.length` の平均と
`dangerous` 発生率を固定点と比較している。フェーズ1の回帰確認にも同じ手法を使うべき。

### 3.2 牝馬本人の出現が最初から存在しない

3.1 を直しても、ダンスパートナー **本人** の出現はどこにも無い
（セルが無く、`mareNodeIds` にも入らない — 3.3 参照）。
ダンスインザダーク×ダンスパートナーの全兄妹クロスを出すには、
プレースホルダー・サブツリーの根に
「牝馬本人（index=null、sex=female、nodeId=彼女のノード）」の出現を作る必要がある。

§4.1 の ref 整備は自家製馬だけを対象に書かれているが、**マスタ繁殖牝馬を祖先に置いた
場合にも同じ「セルを持たない個体」の問題があり、そちらが先に効く**。

### 3.3 祖先セルを差し替えても15牝馬枠が更新されない

`mareNodeIds` は `setDataForPedigree` の **list[0] にしか** 付かず
（pedigree-builder.js:99-105）、`buildMareOccurrences` は `selected[0]` と `selected[16]`
しか読まない（inbreed-detector.js:127）。

**実行確認**: 母側ルートにエアグルーヴを置いた後、cell19 にダンスパートナーを置いても、
`selected[16].mareNodeIds` は15枠すべて **エアグルーヴのまま変化しない**。
本来 `MM` 枠は ダンスパートナー になるべきところが シャダイフェザー のまま。

つまり祖先セルを1つでも手で差し替えると、牝馬15枠は **画面に無い血統** を指したまま
クロス判定に参加する。逆に、差し替えで持ち込んだ馬の牝馬情報は捨てられる。

これは既存バグだが、仕様書の受入テスト A02 / D02 / D05 はこれが直っている前提で書かれている。
§4.1 の「mareRefs を伝播する」は保存時の話しか書いていないが、
**実際に必要なのはセル変更のたびに15枠を再計算すること**。

### 3.4 表示分類の取りこぼし（軽微）

表示ノードが1件しか無いクロスは、`new Set(identityValues).size === 1` により必ず
`sameNameGroups`（同名クロス）へ倒れる（inbreed-detector.js:1483 付近）。
全兄妹クロスなのに同名クロスとして表示される。
牝馬側の表示を抑制すると片側1件のクロスが増えるので、§6 の実装とセットで直す必要がある。

## 4. §5-2 をそのまま実装すると偽陽性が出る

`isExactSameNode`（inbreed-detector.js:37）は、
**両方の nodeId が文字列でないときに名前一致へフォールバック** する。

```javascript
if (nodeTable && typeof a?.nodeId === "string" && typeof b?.nodeId === "string") {
  return a.nodeId === b.nodeId;
}
return a?.name === b?.name;   // ← ここ
```

★☆馬・自家製馬・エディット種牡馬は全員 nodeId が null なので、
§5-2 の「★／☆という名前を理由に除外しない」を実装した瞬間、この行が開く。

| 種別 | 現行 | 除外をやめた後 |
|---|---|---|
| ★薄め馬（`pedigree-cells.js:387` が `★1薄めダンスインザダーク` のように自動生成） | 除外 | **左右で同じ名前になれば同一馬として結合** |
| ☆自家製馬 | 除外 | **同じ題名で別個体を保存すると同一馬扱い** |
| エディット種牡馬（`horse-loading.js:168` で nodeId=null、name はベース馬と同名） | **今も名前一致でベース馬とクロスしている** | §4.1「edit は名前空間を分離」を素直に実装すると **この既存クロスが消える** |

仕様書 D03 はこの偽陽性を検知するテストになっているが、本文に対策が書かれていない。
§5 に次を明記すべき。

- nodeTable がある経路では **名前による同一性判定を行わない**。ref が unknown 同士は常に false。
- ★薄め馬の identityRef 種別（`unknown`）を §4.1 の名前空間一覧に追加する。
  現状 master / custom / edit / 未解決 の4種しか無く、★薄め馬がどこに入るか不明。
**エディット種牡馬の扱い（2026-09-08 確定）: 公式の因名版とまったく同じに扱う。**

`docs/settings-and-edit-stallion-design.md` §0・§2-2 が「DB に無い凄馬（因名版）を自分で登録する機能」
「本家とクロスが成立する」「既存の凄馬（アイアンリージ巌瓏 等）と同じ扱い」と明記しており、
設計意図はもともと因名版である。よって §4.1 の「edit を独立した名前空間にする」は採らない。

| 使い方 | 結果 |
|---|---|
| エディット種牡馬**本人**がクロス相手（ベース馬と並ぶ） | クロス**成立**（§6 の同一 pedigreeId ルールに乗せる。pedigreeId はベース馬から継ぐ） |
| エディット種牡馬を自家製馬の**父**に使う | 親比較キーは因名版と同じ variant キー → 全兄妹**不成立** |

例: 「サンデーサイレンス神雷」（ベース 1989）× エアグルーヴ の仔 は
アドマイヤグルーヴと全兄妹に **ならない**。ベースが年号版でも、自作因名を付けた時点で因名版とみなす。
公式因名版の A03（本人が燕闘版でも成立）／B03（父が覇煌なら不成立）と同じ非対称で、規則は1本で足りる。

## 5. §8 の影響範囲から抜けているもの

### 5.1 `vue/logic/plan/plan-diagnosis.js`（工程診断）

`judgeInbreed` の2つ目の呼び出し元（391行 / 424行）。合成した `stepSelected` 盤面を渡す。

- `composeVirtualMareBoard` / `sliceMareBoard` は `board[0]` を null にするので、
  その側の15牝馬枠が丸ごと消える。工程診断は今でも牝馬由来のクロスを取りこぼしている。
- ref を追加するならこの合成盤面にも同じ伝播が要る。さもないと画面のクロス表示と
  工程診断の「危険」判定が食い違う。
- §8 の表にファイルごと追加すること。

### 5.2 因子計算は現行のまま据え置いてよい（仕様書 §6・D04 の書き換えは不要）

**2026-09-08 決定: 光らないセルの因子はカウントしない。実装は「牝馬は常に因子カウントから除外」でよい。**

**根拠（データ確認済み）: 牝馬は因子を持てない。**

- DB の繁殖牝馬 **499頭すべてが因子なし**（種牡馬は 2415頭中 1456頭が因子を持つ）。
- 自家製馬でも、繁殖牝馬として保存すると因子は付かない。
  `vue/CombinationDialog.js:213` が `this.saveKind === 'stallion' ? this.stallionFactors : []`
  で空配列を渡し、UI 側も 508行で種牡馬以外は因子入力欄を非活性にしている。
- 牝馬15枠の出現はそもそも nodeId しか持たず、因子を運んでいない。

したがって**牝馬の表示を抑制しても因子数は変わらない**（もともと 0 なので）。
仕様書 §6 の「因子計算等は完全な内部結果を入力にする」も D04 の
「因子は表示抑制前と同じ」も、結果として成立する。**どちらも書き換え不要。**

実装は `inbreed-ui.js:78` の
`buildInbreedFactorCounts(this.sameNameGroups, this.siblingGroups, this.inbreedList)` を
**現行のまま据え置けばよい**。本レビュー初版の「`crosses` 由来へ差し替える」は撤回する。
§8 の「因子計算・UI呼出元」行も「変更なし」でよい。

3層の整理は次のとおり。

| 層 | 入力 | 牝馬の全兄妹由来の出現 |
|---|---|---|
| 内部 crosses・血量・`dangerous`・理論 | 完全な内部結果 | **含める** |
| 表示（色・ハート） | 表示対象 | 含めない |
| 因子カウント | 表示対象 | 含めない（そもそも因子が無いので差は出ない） |

**将来の注意**: 自家製の繁殖牝馬に因子を付けられるようにした場合、この単純化は崩れる
（`CombinationDialog.js:508` は種牡馬以外でも因子欄のレイアウトを予約しているので、
拡張の可能性はある）。そのときは「牝馬だから除外」ではなく
「全兄妹由来の出現だから除外」へ戻すこと。仕様書に1行残しておく。

なお §6 の「クロス成立の有無を `inbreedColorIndexes.length` だけで判断しない」は、
現行の `legacyHiddenCrossCount`（1391行）が既に担保している
（表示 index を持たないクロスも `count` に加算される）ので、新規の `hasCross` は不要。

### 5.3 `selfAncestorWarning` への言及がゼロ

直近5コミットがまるごとこの機能の調整で、`inbreed-detector.js:1024` にある。
pedigreeId 一致＋同一側の祖先関係で ⚠ を出す。

- 自家製に identity を与えるなら「同じ ch_ を自分の祖先に持つ」を ⚠ に含めるか決める必要がある。
  現行は `pedigreeIdOfNodeId` が null を返すので自家製は素通り。
- 現行の `isSameSideAncestor` は16の牡馬セルしか辿らず、牝馬15枠（index=null）は対象外。
  牝馬を判定に入れるとここの穴が目立つようになる。
- 最低限「本変更では selfAncestorWarning の対象を変えない」と明記すること。

### 5.4 `dangerous` の波及が過小評価されている

自家製を判定に入れると、同じ ch_ を左右ルートに置いた配合は
血量 100000 → `dangerous = true` → theory_08「危険な配合」＋工程診断の ⚠。
全兄妹同士を左右ルートに置いた場合も同じ（実行確認: ダンス2頭で `bloodVolume=100000`）。

現行は ☆除外により必ず不成立なので、**既存の保存配合が一斉に「危険」表示になり得る**。

**2026-09-08 決定: この挙動を受け入れる。** 統合版はまだ未公開で、影響を受ける公開済みデータが無い。
実行確認した血量は次のとおり。

| 同じ自家製個体をどこに置くか | 血量 | dangerous |
|---|---|---|
| 左右ルート（1代目 × 1代目） | 100000 | true |
| 本馬 × 母の父（1代目 × 2代目） | 75000 | true |
| 3代目 × 3代目 | 12500 | false |

積み上げでよくある「自家製種牡馬 X を付けた娘に、また X を付ける」は 1代目×2代目なので
危険になる。極端な近親なので挙動としては正しい。E01 で固定する。

### 5.5 `json/brosData.json`（全兄妹の手動オーバーライド）の位置づけが未定義

`brosData` には ダンスインザダーク ⇔ ダンスパートナー が入っている。
しかし nodeTable がある経路では `isMasterCrossRelated`（= 同一ノード or マスタ親一致）しか使われず、
**`isFullSiblingByOverride` は呼ばれない = brosData は無視されている**
（呼ばれるのは nodeTable 無しの縮退経路と legacy `recognizedCrosses` だけ）。

**調査結果: brosData は不要。マスタ判定へ一本化してよい。**
brosData の全兄妹ペア36件を pedigreeNodes の父母と突き合わせたところ、

- 32件はマスタでも父母が一致する（= マスタ判定だけで拾える）
- マスタでは父母が一致しないペアは **0件**
- 残り4件は英語名・別名によるもので、実体はマスタで拾える
  （Bull Lea = ブルリー、ウィルロック = ダイワルージュ、ハツコイケール = スターリーロマンス）。
  `Harlan's Holiday` / `ハーランズホリデー` は同一馬の別名で、そもそも兄妹関係ではない

したがって brosData が単独で拾えるものは存在しない。
nodeTable 経路では今も無視されているので、そのまま無視し続けてよい。
nodeTable が読めない縮退経路のフォールバックとしてだけ残す。
名前一致ベースなので、nodeTable 経路へ復活させると §4 の偽陽性問題に直結する。

### 5.6 resolver の受け渡し方が未定義

§5 の擬似コードは `resolver.parents(a.ref)` を要求するが、`judgeInbreed` の現行シグネチャは
`(selected, inbreedExceptions, nodeTable)` の純関数で、自家製の保存レコードへ届かない。

- 第4引数で custom registry を渡すのか、nodeTable を包む統合 resolver に差し替えるのか。
- 呼び出し元は `inbreed-ui.js:104` と `plan-diagnosis.js:391,424` の2箇所。両方直す必要がある。
- 純関数性を保つなら、セル側に `fatherRef` / `motherRef` を焼き込んで渡す案もある
  （resolver 不要になるが pedigree-builder 側の伝播が増える）。

**推奨: resolver を第4引数で渡す + セルには ref だけ載せる、の併用。**

- 親の解決（自家製の父母）は **resolver**。セルへ焼き込むと `plan-diagnosis.js` の
  合成盤面すべてに伝播が要る。`composeVirtualMareBoard` は `board[0]` を null にするなど
  情報が落ちる経路があり、焼き込み方式はそこで破綻する。resolver なら呼び出し元2箇所を
  直すだけで済む。
- 個体の識別（誰であるか）は **セルの ref**。resolver では引けない。理由は、
  `saved-horse-builder.js` が `id` / `customHorseId` を祖先セルへ意図的に写していないため
  （BADGE_FIELDS のコメント参照）、祖先にいる自家製馬は現状セル上で無名になる。
  §4.1 の identityRef 伝播はここを埋めるもので、resolver では代替できない。

**どちらを採るかは仕様書が決めること。** Codex に選ばせると2つの呼び出し元で食い違う。

### 5.7 至高（SUPREME）は現行式を維持する。修正で偽陽性が1つ消える

**2026-09-08 決定: 現行式のまま。全兄妹が1頭でも群に混ざったら至高は不成立でよい。**
自家製の全兄妹（例: サンデーサイレンス1989 × ウインドインハーヘア の自家製馬）でも同じく不成立。

`evaluateSupremeCross`（`inbreed-detector.js:1305`）は、クロス群の
**全出現が同一実馬**（nodeId 一致、または pedigreeId 一致）であることを要求する。
一方でクロス群の統合は `isMasterCrossRelated`（同一馬 **または全兄妹**）で行われるので、
全兄妹が群に吸収されると `allSameHorse` が false になり至高が落ちる。
これはユーザーの期待どおりの挙動である。

**実行確認（マスタ馬の場合。現行でも期待どおり動く）**

```
ディープインパクトを 3代(翔燕) / 4代(央獅) / 5代(煌魂) / 母側3代(通常版) に配置
  群: ディープ@2 + ディープ@4 + ディープ@8 + ディープ@18   → 至高 = [2,4,8,18]

母側4代目にブラックタイド（ディープの全兄）を1頭追加
  群: ディープ@2 + ディープ@4 + ディープ@8 + ディープ@18 + ブラックタイド@20
                                                          → 至高 = []
```

**実行確認（自家製の場合。現行はここが誤っている）**

同じ盤面の母側4代目へ「サンデーサイレンス1989 × ウインドインハーヘア」の自家製馬を置くと、
現行は ☆除外により群に入らないため **至高 = [2,4,8,18] のまま成立してしまう**。
ゲームでは不成立なので、これは現行の**偽陽性**である。

したがって §5.7 は「至高が消えるリスク」ではなく、
**フェーズ2 が偽陽性を1つ潰す**という位置づけになる。仕様書 §7 に
「至高の判定式は変更しない。ただし自家製・牝馬が判定に入ることで、
これまで誤って成立していた至高が正しく不成立になる」と書くこと。

なお他の理論への波及は無い。奇跡（MIRACLE）は `selected[4..7]` と `selected[19]` の
セル比較だけで、クロスを見ていない。面白・見事・完璧・超完璧は親系統配列のみ。
クロス由来で動くのは `DANGEROUS`（§5.4）と `SUPREME` の2つだけである。

### 5.8 共有・保存時の自家製馬同梱（`vue/CombinationDialog.js`）

`collectCustomHorseIds`（`CombinationDialog.js:263`）は32セルを走査して
`source === 'custom' || customHorseId` を持つセルの id を集め、`config.customHorses` に同梱する。

しかし `saved-horse-builder.js` は `id` / `customHorseId` を祖先セルへ写さないので、
**集まるのは実質ルートセル（0 / 16）だけ**。積み上げで祖先にいる自家製馬は同梱されない。

現状は「祖先セルに識別子が無い＝復元するものも無い」ので破綻していないが、
§4.1 で祖先セルへ identityRef を伝播させた瞬間、
**受け取り側にレコードが無い ref を指す config** ができる。
仕様書 §4.1 の「共有・エクスポートに必要な祖先レコードも同梱する」はこの話だが、
§8 の実装箇所表に `CombinationDialog.js` が無い。追加すること。

## 6. 同一実馬の別 variant 同士の扱い（2026-09-08 確定）

**決定: クロスとして出す。** ただし内部の呼び名を「同一馬」へ直す。

**実行確認（現行）**: パーソロン1971（`-01`）と パーソロン覇煌（`-10`）を左右に置くと
`siblingGroups=[[2,17]]` になる。`isExactSameNode` は nodeId が違うので false、
`parentsOf` が両方とも同じ pedigree ID を返すので `isFullSiblingByMasterNodeIds` が true になり、
**全兄妹クロスとして**成立している。

つまりクロスが出ること自体は現行どおりでよい。直すのは分類だけ。

```javascript
// 同一 pedigreeId は「同一馬」として成立させる
isExactSameNode: nodeId 一致 または pedigreeId 一致 → true
// 全兄妹判定からは同一 pedigreeId を除外する
isFullSibling:   pedigreeId が一致するなら false（同一馬なので兄妹ではない）
```

- **注意**: 全兄妹判定にガードだけ足して同一馬側に足さないと、**クロスが消える**。
  本レビュー初版はガードだけを書いていたので誤り。必ず両方入れること。
- `isSameBranch` も `isFullSiblingByMasterNodeIds` で枝の親を比べているので、同じ扱いに揃える。
- `selfAncestorWarning`（`inbreed-detector.js:1024`）はすでに pedigreeId 一致で判定しているので、
  この変更で意味論が揃う。
- なお `sameNameGroups` と `siblingGroups` は `buildInbreedFactorCounts` で同一に扱われ、
  画面表示も共通なので、**この分類変更は現状の見た目を変えない**。
